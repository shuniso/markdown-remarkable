# セキュリティ

このドキュメントは `mdview` に対して行ったセキュリティ監査の結果をまとめたもの。

## 保証していること

- すべての処理はローカルで完結する。アプリ自身が外部ネットワークへ何かを送信することはない。
  - 依存クレートに HTTP クライアント（`reqwest`/`hyper`/`ureq` 等）は含まれていない。
  - ソケットを開くのは `--browser` モードのみで、`127.0.0.1:<port>`（ループバック）にしかバインドしない。ネイティブウィンドウ・`--export` はソケットを一切開かない。
  - テレメトリ・アップデートチェック・クラッシュレポート等の類は存在しない。
- 読むファイルは次の5種類だけ:
  - 開いている Markdown ファイル本体。
  - その隣のレビューサイドカー `<file>.review.json`。
  - ウィンドウ位置/サイズを保存する `window.json`（OS 別の設定ディレクトリ配下）。
  - 開いた md の親ディレクトリ配下の画像ファイル（`GET /asset?p=...`、ライブ表示のみ
    — `--export` では発生しない）。拡張子 allowlist
    （png/jpg/jpeg/gif/webp/bmp/svg/avif/ico）、`..`/絶対パス/シンボリックリンク脱出は
    拒否（`canonicalize` した結果が親ディレクトリの canonicalize 結果を prefix に持つ
    ことを確認）、20 MiB 上限。
    - **ハードリンクは検出できない**: シンボリックリンクは `canonicalize` がリンク先へ
      解決するため脱出チェックで弾けるが、ハードリンクは別パスとして存在する同一
      inode であり `canonicalize` では見分けが付かない。ドキュメントの親ディレクトリ
      内に、拡張子が allowlist に一致するファイル名でその外側のファイルへのハード
      リンクが置かれていた場合、そのファイルは読める。信頼できないアーカイブを展開
      してその中の md を開く、といった使い方では注意すること（同一ファイルシステム
      内でのみ作成できるため、攻撃者が任意にハードリンクを仕込める状況は限定的では
      ある）。
    - **`canonicalize` と実際の読み取りの間の TOCTOU は未対策**: チェック時点で
      対象ディレクトリ配下を指していたパスが、`canonicalize` 後・`fs::metadata`/
      `fs::read` 実行前に差し替えられる（対象が削除されて配下外を指す同名のシンボ
      リックリンクに置き換わる、等）競合には対処していない。同じマシン上の別プロ
      セスがそのタイミングでファイルシステムを操作できる環境（`--browser` の露出
      面と同様）でのみ意味のある脅威。
  - `root_dir`（そのウィンドウが**最初に開いたファイルの親ディレクトリ**、canonicalize
    済み・以後そのウィンドウが生きている限り変わらない — `docs/superpowers/specs/
    2026-08-29-file-tree-design.md` の「root_dir」節参照）配下の他の `.md`/`.markdown`
    ファイル（左ペインのファイルツリーからの切り替え、`PUT /open` — ネイティブウィンドウ
    のみ。`--browser` は `501` を返し切り替えない、CLI で指定した1ファイルに固定された
    まま）。パス検証:
    - `Component::Normal` のみ・拡張子 `.md`/`.markdown`（画像と同じ関数を再利用）。
    - 対象パス自身が `symlink_metadata` でシンボリックリンクでないことを確認
      （`canonicalize` 前 — エスケープ先が範囲内に収まる symlink であっても拒否する。
      `GET /tree` が symlink を一切列挙しないことと揃えるための、下記のエスケープ
      チェックより厳しいチェック）。
    - `canonicalize` した結果が `root_dir` の canonicalize 結果を prefix に持つこと
      （画像と同じエスケープチェック）。
    - `canonicalize` 後の対象が `fs::metadata(..).is_file()` であること（ディレクトリ
      や FIFO・デバイスノードを `.md` という名前で掴んで `read_to_string` が UI
      スレッドをブロックするのを防ぐ）。
    `GET /tree` の除外リスト（隠しフォルダ・`node_modules` 等）・深さ上限は表示上の都合
    でありここでの許可範囲には影響しない。切り替え後はそのファイルが「開いている
    Markdown ファイル本体」になり、以降は最初の箇条書きと同じ扱い（サイズ上限なし、
    他の箇条書きと同じハードリンク非検出/TOCTOU 未対策が適用される）。
  - `GET /tree`（同じく左ペインのファイルツリー）はファイル**内容**を読まないが、
    `root_dir` 配下を深さ4・上限2000件（超えたら `truncated: true`）までディレクトリ
    走査し、`.md`/`.markdown` を含むディレクトリ名・ファイル名を列挙して返す。
    加えて、pruning 前の**訪問エントリ数**自体にも上限 20000 を設けている
    （md を含まない巨大なディレクトリツリーが応答に一切現れなくても、走査そのものが
    UI スレッドを長く塞ぐのを防ぐため）。隠しディレクトリ（`.` 始まり）・
    `node_modules`・`target` はスキップし、シンボリックリンクは `DirEntry::file_type`
    （`symlink_metadata` 相当）で判定して辿らない。非 UTF-8 のファイル/ディレクトリ名は
    一覧から除外する（`to_string_lossy` の U+FFFD 混じり表示は `PUT /open` で開けない
    ため、出しても意味がない）。
- 書くファイルは次の4種類だけ:
  - レビューサイドカー `<file>.review.json`（`PUT /review`）。
  - レビューのエクスポート `<stem>.review.md`（`POST /export` / パネルの Export ボタン）。
  - `window.json`（ウィンドウの移動・リサイズ後、デバウンスして保存）。
  - `--export` の出力先 `OUT.html`。
  - いずれも tmp ファイルを `OpenOptions::create_new` で作成してから `rename` する方式で書き込む。既存ファイルと同名のシンボリックリンクが仕込まれていても、そのリンク先を追従して上書きすることはない（`create_new` はそこに何か存在すれば失敗する）。

## 例外（意図的にガードの外にあるもの)

1. **リンククリックはアプリ外に委譲される**: `http(s):`/`mailto:` リンクをクリックすると OS の既定ブラウザ/メールクライアントが起動する（ネイティブウィンドウにはアドレスバーも戻るボタンもないため）。開いた先で何が起きるかは `mdview` の管理外。
2. **外部画像は既定でブロックされる**。Content-Security-Policy の `img-src` は既定で `data: 'self'` のみで、ドキュメント中の `http(s)` 画像はリクエストされず、壊れた `<img>` として表示される（`'self'` は同一オリジンの `/asset`—上記のローカル画像—を許可するためのもので、外部ホストへのリクエストは相変わらず発生しない）。`--allow-remote-images` を付けたときだけ `http(s)` 画像も読み込まれるようになり、画像 URL が指すホストにビューアーの IP アドレスが露出する（メール/RSS クライアントの「トラッキングピクセル」対策と同じ理由でのオプトイン）。
3. **`--browser` 実行中は、同一マシン上の他プロセスが `127.0.0.1:<port>` 経由で文書とコメントを読み書きできる**。認証は一切ない（`X-Mdview-Request` ヘッダはブラウザの CORS プリフライトを利用した CSRF 対策であり、認証機構ではない）。同じマシンを使う別ユーザー/別プロセスからのアクセスを想定していない用途では `--browser` を避けるか、信頼できる環境でのみ使うこと。ネイティブウィンドウ（既定モード）にはこの露出面はない。
4. **WebView エンジン自体（WebView2 / WKWebView / webkit2gtk）と OS との通信は `mdview` の管理外**。特に Windows の WebView2 Runtime はエンジン自身の自動更新など、`mdview` から見えない/制御できない通信を行うことがある。

## ログ

- ログは stderr のみに出力される。ファイルへのログ書き込みは一切行わない。
- 警告メッセージにはファイルのフルパスが含まれることがある（例: 読み込み失敗時の `warning: failed to read <path>: ...`）。stderr の出力先には注意すること。
- `MDVIEW_DEBUG=1` を設定すると、`--browser`/ネイティブウィンドウが受け取った各リクエストについて method・path・status・（`PUT`/`POST` の場合のみ）本文のバイト数を1行ずつ出力する。本文の中身そのものは出力されない。
- クライアント供給の値（例: `PUT /review` の `doc.file`）は、内容そのものではなくバイト長のみをログする — 任意の文字列を stderr に混入させられないようにするため。

## 環境変数

`mdview` が読む環境変数は次の4つのみ:

- `HOME` — macOS/Linux での `window.json` の保存先解決に使用。
- `XDG_CONFIG_HOME` — Linux での `window.json` の保存先解決に使用（未設定なら `$HOME/.config` にフォールバック）。
- `APPDATA` — Windows での `window.json` の保存先解決に使用。
- `MDVIEW_DEBUG` — 上記のリクエストログを有効化する（値は何でもよく、設定されているかどうかだけを見る）。
